## 1. Problem Statement

Two completed feature passes (`.ai/features/completed/large-note-performance-codemirror/`, `.ai/features/completed/codemirror-unified-editor/`) replaced the `<textarea>` source editor with CodeMirror 6 and bolted a Live-Preview decoration plugin and the existing TipTap-era formatting toolbar onto it. Both passes were verified only with `npm run test:js`, `vue-tsc`, `pint` and `php artisan test`. **Nobody rendered the editor in a browser.**

The verification gap is structural, not accidental:

- `vite.config.ts:45-48` sets `test.environment: 'node'`. No test in `tests/js/` can mount an `EditorView` or a Vue component, so every defect that only exists in the DOM, in the CSS cascade or in Vue's reactivity graph is invisible to the suite.
- `tests/js/editor/toolbarCommands.test.ts:31-60` drives the shared toolbar command table **through a TipTap `Editor` only**. Every CodeMirror branch of that table (`toolbarCommands.ts:77-257`) is untested — including three branches that are no-ops or actively destructive.
- `tests/js/editor/codemirrorLivePreview.test.ts` (16 lines) asserts only that `EditorState.create()` does not throw. It never builds a single decoration.

A real user reports broken toolbar/formatting, broken live-preview rendering, and broken layout/styling/dark mode. This document enumerates the concrete, code-level causes found by audit, one requirement per defect. Each requirement cites the file and line range that produces it.

---

## 2. Goals & Non-Goals

### In Scope (Goals)
- Make every toolbar button in CodeMirror mode do what its label and tooltip promise (Master Plan §53 toolbar list).
- Make the Live-Preview decorations correct (right lines, right positions, never crashing the plugin) and styled through CodeMirror's own theme so the CSS actually applies.
- Make the editor chrome — sizing, spacing, split view, dark mode, gutter alignment, scrolling — consistent with the surrounding app shell.
- Make the rendered Markdown preview safe and correct (frontmatter, attribute escaping, protocol allowlist, debounce).
- Add test coverage that is possible in a `node` environment and that would have caught these defects.

### Out of Scope (Non-Goals)
- Removing TipTap / `TiptapEditor.vue` / `assessMarkdown` / `FrontmatterPanel`, which ADR `codemirror-unified-editor` §Decision-1 called for and the implementation did not do (see Q2). This bug-fix pass keeps both editors working.
- Hiding Markdown syntax markers on inactive lines (Obsidian-style "live preview"). The accepted ADR specifies styled-but-visible markers; changing that is a new feature.
- Adding a DOM test environment, `@vue/test-utils`, `jsdom` or `happy-dom` (new dependencies — see Q1).
- Any backend, schema, service or route change. This feature touches `resources/js/**` only.
- Editor features not already present (tables toolbar button, image handling, autocompletion, search panel).

## 3. User Personas & Stories

- **As a** note author,
  **I want to** click Bold, Italic, Link, Divider, Paragraph and Clear formatting and see the Markdown change correctly,
  **So that** I do not have to remember Markdown syntax or discover by trial that half the toolbar is inert.

- **As a** note author using keyboard shortcuts,
  **I want** `Ctrl+B`, `Ctrl+I`, `Ctrl+K` and the other shortcuts printed in the tooltips to work,
  **So that** the tooltips are not lying to me.

- **As a** note author with YAML frontmatter and fenced code blocks,
  **I want** my frontmatter and my shell comments to render as frontmatter and comments,
  **So that** the editor does not show a 24px bold heading in the middle of a bash snippet.

- **As a** note author in dark mode,
  **I want** the editor surface to match the card it sits in and the preview pane beside it,
  **So that** the split view does not look like two different applications.

- **As a** note author with a long note and line numbers enabled,
  **I want** line number N to sit beside line N,
  **So that** I can trust the gutter and the scrollbar.

## 4. Functional Requirements

### Category 1 — Toolbar and formatting commands

| ID | Requirement | Description (mechanism + what the user sees) | Acceptance Criteria |
|---|---|---|---|
| **FR-01** | Toolbar state must track the CodeMirror view | `EditorToolbar.vue:57` calls `useEditorTick(() => activeEditor.value)`. `useEditorTick.ts:23-29` subscribes **only** via `editor.on('transaction', …)` — a TipTap API. A CodeMirror `EditorView` has no `.on`, so `tick` is never incremented. `isActive()`/`canRun()` (`EditorToolbar.vue:59-69`) read `tick.value`, so the only re-render they ever get is the single one at mount when `SourceEditor.vue:102` assigns the `shallowRef`. **Every active-state highlight in CodeMirror mode is frozen at "cursor at position 0, no selection" for the life of the component.** The user moves the caret into `**bold**`, into a `## heading`, into a list — no button ever lights up; the toolbar gives zero feedback. | Given the caret is inside `**bold**`, When the user clicks elsewhere and back, Then the Bold button's `aria-pressed` reflects the current caret position; and the same for italic, strike, code, h1–h3, bulletList, orderedList, taskList, blockquote. |
| **FR-02** | Undo/Redo enablement must come from history depth | `toolbarCommands.ts:83,90` return `Boolean(editor)` for `canRun` in the CodeMirror branch, so Undo and Redo are **always** rendered enabled (`EditorToolbar.vue:152,165`), including on a freshly opened note with an empty history, where clicking does nothing. | Given a freshly opened note, When the toolbar renders, Then Undo and Redo are `disabled`; When the user types, Then Undo becomes enabled; When the user undoes, Then Redo becomes enabled. |
| **FR-03** | Italic must not strip bold, and inline code must not strip fences | `toggleInlineMark` (`codemirrorCommands.ts:22-39`) and `isInlineMarkActive` (`toolbarCommands.ts:52-63`) decide "already wrapped" by slicing exactly `marker.length` characters either side of the selection. For `marker === '*'` and the text `**bold**` with `bold` selected, `sliceDoc(from-1, from) === '*'` and `sliceDoc(to, to+1) === '*'`, so both report *italic active* and `toggleItalic` takes the **unwrap** path at line 29-38: it deletes one `*` from each side and turns `**bold**` into `*bold*`. **Clicking Italic on bold text silently removes the bold instead of adding italic**, and the Italic button is lit on every bold word. The same single-character blindness applies to `` ` `` inside a ``` ``` ``` fence delimiter. | Given `**bold**` with `bold` selected, When the user clicks Italic, Then the document contains `***bold***` and the bold is preserved; Given the same selection, When the toolbar renders, Then Italic is not reported active while Bold is. |
| **FR-04** | Paragraph must clear the line prefix | `toolbarCommands.ts:123` maps Paragraph to `toggleLinePrefix(editor, '')`. In `toggleLinePrefix`, `allHavePrefix = lines.every(line => line.text.startsWith(''))` (`codemirrorCommands.ts:91`) is **always true** because every string starts with the empty string, so the function always takes the removal branch and pushes `{from: line.from, to: line.from + 0, insert: ''}` — a zero-length, zero-content change. **Paragraph is a complete no-op**; it can never strip a `#`, `- ` or `> ` prefix, which is the only thing it exists to do. The button is enabled in the overflow menu (`EditorToolbar.vue:389-401`). | Given the caret on `## Title`, When the user clicks Paragraph, Then the line becomes `Title`; Given the caret on `- [ ] task`, When the user clicks Paragraph, Then the line becomes `task`; Given a plain line, Then the command leaves it unchanged and reports no change. |
| **FR-05** | Divider must insert a rule on its own line and not consume the current line's marker | `toolbarCommands.ts:237` maps Divider to `toggleLinePrefix(editor, '---\n')`. A prefix containing `\n` can never match `line.text.startsWith(prefix)`, so the insert branch runs; that branch replaces `line.from` → `cleanFrom`, where `cleanFrom` has skipped the line's existing list/heading/quote marker (`codemirrorCommands.ts:101-107`). **Clicking Divider on `- item` deletes the `- ` and produces `---\nitem`**; on `## Title` it produces `---\nTitle`. With a multi-line selection it injects `---` before *every* selected line. No selection is set afterwards, so the caret lands unpredictably. | Given the caret on `- item`, When the user clicks Divider, Then the document is `- item\n\n---\n` with the list marker intact and the caret on the line after the rule; Given a multi-line selection, Then exactly one rule is inserted. |
| **FR-06** | Clear formatting must work in CodeMirror mode | `toolbarCommands.ts:247-250`: the CodeMirror branch of `clearFormatting.run` is literally `: true` — it returns success without dispatching anything. `canRun` returns `Boolean(editor)`, so the button (`EditorToolbar.vue:360-371`, plus the overflow menu) is enabled and does nothing. Master Plan §53 lists "Clear formatting" as a required toolbar action. | Given the selection `**bold** and *italic* and `code``, When the user clicks Clear formatting, Then the selection becomes `bold and italic and code`; Given the caret on `> ## Quoted`, Then the line prefix is removed as well. |
| **FR-07** | Link insertion with no selection must produce usable link text | `insertLink` (`codemirrorCommands.ts:201`) computes `const selectedText = text ?? state.sliceDoc(from, to) ?? 'link'`. `sliceDoc` returns the **empty string** for an empty selection, never `null`/`undefined`, so `??` never reaches the `'link'` fallback. **With no selection, the Link dialog produces `[](https://example.com)`** — a link with no text, which renders as an invisible anchor in the preview. The caret is also parked after the whole insertion (`anchor: from + insertion.length`) rather than inside the label. | Given no selection, When the user applies `https://example.com`, Then the document gains `[link](https://example.com)` with `link` selected so it can be typed over; Given a selection, Then the selected text becomes the label. |
| **FR-08** | The Link dialog must prefill, edit and remove the link under the caret in CodeMirror mode | `EditorToolbar.vue:126-134`: `currentHref()` returns `''` unless the editor has `getAttributes` (a TipTap method), so in CodeMirror mode the URL field is **always blank**, even with the caret inside `[text](url)`. `LinkDialog.vue:60-65` then calls `insertLink`, which *inserts at the caret* instead of replacing the existing link — producing nested garbage such as `[te[](new)xt](url)`. `LinkDialog.vue:71-80`: `remove()` only handles the `'chain' in active` (TipTap) case, so in CodeMirror mode **Remove closes the dialog and does nothing**. `EditorToolbar.vue:447` passes `:view="activeEditor as any"`, which is how this type mismatch escaped `vue-tsc`. | Given the caret inside `[text](https://a.test)`, When the user opens the Link dialog, Then the URL field contains `https://a.test`; When the user applies `https://b.test`, Then the line becomes `[text](https://b.test)` with no nesting; When the user clicks Remove, Then the line becomes `text`. |
| **FR-09** | Link hrefs must be protocol-validated in CodeMirror mode | `tests/js/editor/toolbarCommands.test.ts:81-94` proves the TipTap path rejects `javascript:alert(1)`. The CodeMirror path (`LinkDialog.vue:60-65` → `insertLink`) performs **no validation** and writes the href verbatim, and `error` (`LinkDialog.vue:32`) is only ever set in the TipTap branch so the user gets no feedback. This is the ingress for FR-20. | Given the URL `javascript:alert(1)`, When the user clicks Apply in CodeMirror mode, Then no link is inserted and the dialog shows an error; Given `https://`, `http://` or `mailto:`, Then the link is inserted. |
| **FR-10** | The keyboard shortcuts advertised in the tooltips must exist in CodeMirror mode | `toolbarCommands.ts` declares shortcuts for 14 commands (`Ctrl+B`, `Ctrl+I`, `Ctrl+E`, `Ctrl+Shift+X`, `Ctrl+Alt+1..3`, `Ctrl+Shift+7/8/9/B`, `Ctrl+Alt+C`, `Ctrl+\``), `EditorToolbar.vue:77-83` renders them into every `title`, and `EditorToolbar.vue:319` advertises `Link (Ctrl+K)`. `buildCodeMirrorExtensions` (`codemirror.ts:97`) registers only `defaultKeymap`, `historyKeymap` and `indentWithTab` — **none of these bindings exist**, so every advertised shortcut is a no-op left to the browser's default `contenteditable` handling. The only working shortcut is `Ctrl+S`, handled at the window level in `NoteEditor.vue:283-288`. | Given the caret in the editor, When the user presses `Ctrl+B`, Then the bold command runs and the browser's own formatting is suppressed; and likewise for every shortcut string printed by `toolbarCommands.ts`; When the user presses `Ctrl+K`, Then the Link dialog opens. |

### Category 2 — Live preview rendering

| ID | Requirement | Description (mechanism + what the user sees) | Acceptance Criteria |
|---|---|---|---|
| **FR-11** | Live-preview decorations must not apply inside fenced code blocks or YAML frontmatter | `buildLiveDecorations` (`codemirrorLivePreview.ts:55-158`) is a pure per-line regex scan with no awareness of block context. Consequences the user sees on almost every real note: (a) `# !/bin/bash` or `# TODO` inside a ``` fence renders as a 24px bold H1 with a bottom border (`:67-89`); (b) the `---` delimiters of a YAML frontmatter block match the horizontal-rule regex (`:103`) and render as a transparent-text rule, so **every note with frontmatter opens with a broken-looking band at the top**; (c) `> ` and `- [ ]` inside a fence are decorated as a blockquote / checkbox widget. `@codemirror/lang-markdown` is already installed and parses all of this correctly; the plugin just ignores the tree. | Given a note whose body contains a fenced block containing `# comment`, When it renders, Then that line carries no heading decoration; Given a note that opens with a `---` YAML frontmatter block, Then neither delimiter is decorated as a horizontal rule and no key line is decorated as a heading; Given `# Real heading` outside any fence, Then it is still decorated. |
| **FR-12** | Building the decoration set must never throw, and the plugin must never silently deactivate | `RangeSetBuilder.add` requires strictly non-decreasing `from`. The scan loop (`codemirrorLivePreview.ts:59-62,153`) iterates `view.visibleRanges` and restarts at each range's `from`. CodeMirror splits visible ranges **inside** a single long line when it inserts line gaps, so the same line can appear in two consecutive ranges; the second pass then calls `builder.add(line.from, …)` with a `from` lower than an already-added range and the builder throws `RangeError`. CodeMirror catches exceptions thrown from a `ViewPlugin`'s constructor/`update` via `logException` and **deactivates the plugin**, so the whole live preview silently dies for the rest of the session — decorations freeze mid-document and never update again. This is the most likely mechanism behind "decorations rendering inconsistently". | Given a document containing a single line long enough for CodeMirror to create line gaps, When the viewport changes, Then no exception is logged and decorations continue to update; the decoration builder must process each line at most once per build. |
| **FR-13** | Live-preview decorations must not put vertical margins on `.cm-line` | `livePreview()`'s theme sets `marginTop`/`marginBottom` on `.cm-heading`, `.cm-heading-1` and `.cm-heading-2` (`codemirrorLivePreview.ts:183-194`), and the horizontal-rule decoration carries the Tailwind class `my-2` (`:108`). CodeMirror measures each line block with `getBoundingClientRect().height`, which **excludes margins**, and then sizes `.cm-gutterElement` and the scroller's height map from those measurements. Every heading and rule therefore adds height that CodeMirror does not know about, so: line numbers drift progressively out of alignment with their lines down the document, `posAtCoords` misses (clicking puts the caret on a neighbouring line), and scrolling/`scrollIntoView` jumps. Spacing must be expressed as padding, which `getBoundingClientRect` does include. | Given a 300-line note containing ten headings with line numbers enabled, When the user scrolls to the bottom, Then each line number is vertically aligned with its line; When the user clicks on a line, Then the caret lands on that line; no CodeMirror theme rule or decoration class may set `margin-top`/`margin-bottom`/`margin` on `.cm-line`. |
| **FR-14** | Live-preview styling must come from the CodeMirror theme, not from Tailwind utility classes | Decorations pass Tailwind utilities as decoration classes (`codemirrorLivePreview.ts:73-86,97,108,119,138`). Tailwind v4 emits all utilities inside `@layer utilities` (`resources/css/app.css:1`), while CodeMirror injects its theme as **unlayered** CSS via `style-mod`. Unlayered author CSS wins over any layered CSS regardless of specificity, and the generated selectors are `.ͼN .cm-line` (0,2,0) against `.pb-1` (0,1,0) — so CodeMirror wins twice over. Concretely dead today: `pb-1` and `pb-0.5` on headings, `pl-2.5` on blockquotes and `px-2` on code fences are all overridden by the `padding: 0 4px` **shorthand** in `buildTypographyTheme` (`codemirror.ts:69-71`), so the blockquote accent bar sits flush against its text, the heading underline has no breathing room, and the fence band has no inset. Likewise `bg-muted/20` on a blockquote line is overridden by `highlightActiveLine`'s unlayered `.cm-activeLine` background whenever the caret is on that line, so **the blockquote tint flickers off as you move through it**. | Given a blockquote line, When it renders, Then its left inset and background are present; When the caret moves onto it, Then its background does not change; all live-preview visual properties are defined in an `EditorView.theme`/`HighlightStyle`, and no decoration class relies on a Tailwind utility for a property CodeMirror's own CSS sets. |
| **FR-15** | Heading sizes must scale with the `font_size` preference and match the preview pane | `codemirrorLivePreview.ts:73-86` uses absolute Tailwind sizes (`text-2xl` = 1.5rem, `text-xl` = 1.25rem, `text-lg` = 1.125rem, `text-base`, `text-sm`), while the editor's base size is set in **pixels from the user preference** (`codemirror.ts:50-53`) and the preview pane's `.tiptap-content` headings are **em-relative** (`resources/css/app.css:209-231`, `2em`/`1.5em`/`1.25em`). So with `font_size: 20` an H1 (24px) is barely larger than body text; with `font_size: 11` headings are grotesque; and in Split view the same H1 is a different size on the left and the right. ADR `codemirror-unified-editor` §Decision-2 specifies `H1 = 2em, H2 = 1.5em, H3 = 1.25em`. | Given `font_size: 20`, When a `# Heading` renders in the editor, Then its computed size is `2 × 20px`; Given Split view, Then the H1–H3 scale matches the preview pane; `text-{size}` utilities are no longer used for heading decorations. |
| **FR-16** | Fenced code blocks must style their body, not only the delimiter lines | `codemirrorLivePreview.ts:114-121` decorates only lines matching `/^```/`, so a fenced block renders as **two grey bands with unstyled text between them** instead of the "code block background containers and borders" the ADR specifies. | Given a fenced block of three code lines, When it renders, Then the delimiter lines and the body lines share one continuous monospace container with a top border on the opening line and a bottom border on the closing line. |
| **FR-17** | Task checkboxes must toggle reliably and must never mutate a read-only or frozen document | Two defects in `TaskCheckboxWidget`: (a) `ignoreEvent()` is overridden to return `false` (`codemirrorLivePreview.ts:50-52`) — the default is `true`. Returning `false` tells CodeMirror *not* to ignore the widget's DOM events, so a click on the checkbox is also consumed as an editor mouse-selection gesture (CodeMirror calls `preventDefault()` on the `mousedown` while taking focus if the editor is not already focused). Clicking the box therefore also jumps the caret into the replaced range, and the first click after the editor has lost focus is unreliable; the `e.stopPropagation()` at `:34` runs on `change`, far too late to stop the `mousedown`. (b) The widget dispatches unconditionally (`:36-43`). `EditorState.readOnly` is never configured anywhere — `codemirror.ts:102-109` only sets `EditorView.editable`, which does not block programmatic dispatch — so **clicking a checkbox still rewrites the file while the editor is frozen for a guarded navigation (`NoteEditor.vue:364-375`) or read-only**, marking the note dirty after the freeze. | Given an unfocused editor, When the user clicks a task checkbox once, Then it toggles and the caret does not jump into the hidden `[ ]`; Given `readonly`/`frozen` is true, When the user clicks a checkbox, Then the input is disabled, no transaction is dispatched and the note does not become dirty. |

### Category 3 — Layout, theming and the rendered preview

| ID | Requirement | Description (mechanism + what the user sees) | Acceptance Criteria |
|---|---|---|---|
| **FR-18** | Dark mode must use the application's theme tokens, not `oneDark`'s hard-coded palette | `SourceEditor.vue:146-153` reconfigures the theme compartment to `oneDark` when `.dark` is on `<html>`. `oneDark` hard-codes `background: #282c34`, `color: #abb2bf`, `.cm-gutters { backgroundColor: #282c34; border: none }` and `.cm-content { caretColor: #528bff }`. The app's dark `--card` is `hsl(0 0% 3.9%)` (`resources/css/app.css:132`) — near black. Because the theme compartment sits **before** the typography compartment in the extension array (`codemirror.ts:110-111`), `oneDark` also wins the precedence fight against `buildTypographyTheme`'s gutter border and caret colour. The user sees a blue-grey rectangle inside a near-black card, with a hard seam against the Split preview pane (`bg-card/60`, `SourceEditor.vue:271`), no gutter separator, and all the live-preview `bg-muted/*` / `border-border/*` tokens — tuned for the near-black card — washed out on `#282c34`. Light mode has no theme at all (`theme.of([])`), so the two modes are styled by completely different systems. | Given dark mode, When the editor renders, Then its background matches `var(--card)` (or is transparent over it), the gutter separator is visible, and the caret uses `var(--primary)`; Given the Split view in dark mode, Then the editor pane and the preview pane share one surface colour; Given a toggle of the app's appearance control, Then the editor restyles without remounting. |
| **FR-19** | The rendered preview must strip YAML frontmatter | `SourceEditor.vue:211-223` hands the raw document to `marked`. For a note starting `---\ntitle: Foo\ntags: []\n---`, CommonMark parses `title: Foo` + `tags: []` as a paragraph and the closing `---` as a **setext H2 underline for that paragraph**. Preview and Split therefore open with the note's YAML rendered as a giant heading. | Given a note with a leading `---` … `---` YAML block, When Preview or Split renders, Then the frontmatter is not rendered as body content (omitted, or shown as a distinct metadata block), and the first rendered element is the note's first body element; Given a note whose body legitimately starts with `---`, Then it still renders as a horizontal rule. |
| **FR-20** | The rendered preview must escape attributes and must not navigate to disallowed protocols | Two defects in the preview pipeline, both reachable from note content (which may arrive from an external editor or a restored backup): (a) the custom link renderer interpolates `href` and `title` into raw HTML with no escaping (`SourceEditor.vue:47-54`) and the result is injected with `v-html` (`:292`), so a title containing a `"` injects arbitrary attributes — e.g. `onmouseover`; (b) `handlePreviewClick` (`:227-242`) calls `event.preventDefault()` **only when the protocol is allowed** (`:235-237`), so a `javascript:` or `data:` href falls through to the browser's default action and executes. FR-09 closes one ingress; the renderer must be safe regardless of how the text got there. | Given a note containing `[x](http://a.test "a\" onmouseover=\"alert(1)")`, When the preview renders, Then no extra attribute is emitted; Given a note containing `[x](javascript:alert(1))`, When the user clicks it, Then nothing is navigated or executed; Given an `https:`/`http:`/`mailto:` link, Then it still opens in a new tab with `noopener,noreferrer`. |
| **FR-21** | The rendered preview must be debounced | `renderedHtml` (`SourceEditor.vue:211-223`) is a computed over `text.value`, which `onChange` (`:93-98`) rewrites on **every keystroke**. In Split view every keystroke therefore re-parses the entire document with `marked` and re-renders it through `v-html`, discarding and rebuilding the whole preview DOM. This is exactly the per-keystroke cost the large-note feature existed to remove, and it is the one path in the editor that still has it. Master Plan §non-negotiable-13 requires debounced work, not per-keystroke work. | Given Split view and a 150 KB note, When the user types continuously, Then the preview re-renders at most once per debounce interval (150–250 ms) and typing latency in the editor pane is unaffected; When the user stops typing, Then the preview reflects the final text. |
| **FR-22** | The editor mode toggle must not expose library names (LOW) | `NoteEditor.vue:644-667` renders a segmented control labelled **"CodeMirror"** and **"TipTap"**, with the tooltip "CodeMirror 6 with live rich preview and formatting toolbar" and the banner text "open in CodeMirror 6 Source mode" (`:768`). These are engineering identifiers in the product UI, and they are a visible residue of ADR `codemirror-unified-editor` §Decision-1 ("delete the rich vs. source mode bifurcation") not having been carried out. Gated on Q2. | Given the editor header, When it renders, Then the two modes are labelled in user language (e.g. "Markdown" / "Rich text") and no banner or tooltip names a third-party library. |

## 5. Non-Functional Requirements

- **Security & Authorization**: No authorization surface changes. FR-09 and FR-20 are security fixes: untrusted note content must never reach `v-html` unescaped, and no code path may navigate to a non-allowlisted protocol. Per Master Plan §non-negotiable-11, nothing in the editor may log document content.
- **Performance**: FR-21 removes the per-keystroke full Markdown re-parse. FR-11's block-context awareness must stay O(visible lines) — use `syntaxTree(state)` over the visible ranges, or a single forward fence/frontmatter scan; do **not** re-parse the whole document inside `buildLiveDecorations`. FR-12's dedupe must not reintroduce a full-document scan. The 150 KB `LARGE_NOTE_THRESHOLD` (`largeNote.ts:7`) behaviour is unchanged.
- **Accessibility & UX**: `aria-pressed` on toolbar buttons must become truthful (FR-01). `disabled` must become truthful (FR-02). Keyboard parity with the advertised shortcuts (FR-10). Vue components keep a single root element. Checkbox widgets must be `disabled`, not merely inert, when the document is read-only (FR-17).
- **Reliability & Data Integrity**: Markdown files remain the source of truth; no change to `createNoteSaver`, the autosave baseline, hashing or the conflict flow. FR-17b closes a path that writes to a file the UI has declared frozen. Every command change must be verified against `tests/js/markdown/roundTrip.test.ts` expectations — the commands write raw Markdown and must not emit syntax the round-trip fixtures reject.

## 6. Technical Constraints & Context

- Framework: Laravel 13 (PHP 8.4) — **no backend change in this feature**.
- Frontend: Inertia v3 + Vue 3 + Tailwind CSS v4; CodeMirror 6 (`@codemirror/view` ^6.43, `@codemirror/state` ^6.7, `@codemirror/commands` ^6.11, `@codemirror/lang-markdown` ^6.5, `@codemirror/language` ^6.12), `marked` ^17.
- **Tailwind v4 emits utilities inside `@layer utilities`; CodeMirror injects unlayered CSS. Unlayered always wins.** This is the governing constraint for FR-13/FR-14/FR-15/FR-18: editor-internal styling belongs in `EditorView.theme` / `HighlightStyle`, not in utility classes.
- **`vite.config.ts:45-48` pins `test.environment: 'node'`.** No DOM is available in `tests/js/`. All new coverage must be exercisable against an `EditorState` or a pure function. This is why `codemirrorCommands.ts` already defines the `CommandTarget` shape (`:5-9`) and why new logic must follow the same pattern.
- Code style: `vendor/bin/pint --dirty --format agent` (no PHP expected), `npm run check:fix`, `npm run types:check`.
- `vite.config.ts:96-99` enables `sortTailwindcss` for `clsx`/`cn`/`cva`; decoration class strings are not sorted, which is further reason to move them out of Tailwind.

## 7. Risks & Assumptions

- **Assumption 1**: The user's three symptom categories are explained by FR-01…FR-21 and no further unreported defect is in play. Risk accepted: this was a code audit, not a browser session. Mitigation: the plan's final task is a scripted manual UI walkthrough the user can run, so anything still broken surfaces immediately rather than after another QA "PASS".
- **Assumption 2**: TipTap mode stays. All shared code (`toolbarCommands.ts`, `EditorToolbar.vue`, `LinkDialog.vue`, `useEditorTick.ts`) must keep both branches working, and `tests/js/editor/toolbarCommands.test.ts`'s existing TipTap expectations must keep passing unchanged.
- **Risk — visual regression in light mode**: FR-18 replaces the "no theme at all" light path with an explicit app-token theme. Mitigation: use transparent backgrounds in both modes so `bg-card` shows through, and keep `syntaxHighlighting(defaultHighlightStyle, { fallback: true })` as the light highlighter so light-mode token colours do not shift.
- **Risk — syntax-tree access during initial parse**: `syntaxTree(state)` can return an incomplete tree for a large document on the first render, which would make FR-11 flicker. Mitigation: use the tree only over `visibleRanges`, and have the plugin rebuild on `update.docChanged || update.viewportChanged || syntaxTree(update.startState) !== syntaxTree(update.state)` so late parse results are picked up.
- **Risk — `@codemirror/theme-one-dark` becomes unused** after FR-18. Removing a dependency needs approval; the plan leaves it installed and merely stops importing it.
- **Risk — the fix set is wide (10 files)**, so a regression could land anywhere in the editor. Mitigation: the plan is ordered so each task is independently shippable, pure-logic first, and each task names the test that proves it.
